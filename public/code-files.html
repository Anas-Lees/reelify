Code tour

The code, file by file.

Every important file in Edu Shorts — what it is, what it does, the key functions inside, and how it talks to the other files around it.

Backend · Node

The Express server that everything else talks to. Handles uploads, AI calls, the TTS fallback chain, persistence, and authentication.

server.js
~1,800 lines·Express + SSE + Gemini + TTS chain
REST API Server-Sent Events AI calls TTS File upload

The single backend entry point. Express boots here, sets up auth + middleware, registers every route, and exits to app.listen().

What lives in this file
  • Upload + text extraction. POST /api/upload-stream accepts a file, sniffs the format (PDF, DOCX, PPTX, image, plain text), and pulls the text — JSZip for OOXML, native Gemini for PDFs/images, officeparser as a fallback.
  • Streaming reel generation. Builds the prompt with buildReelPrompt(settings) (vibe, length, language, quiz difficulty), sends it to Gemini, and emits each reel object over SSE as it appears in the JSON stream — so the user can start watching while the rest is still generating.
  • Image generation. POST /api/image calls Gemini 2.5 Flash Image with the reel's background_prompt and saves the PNG to disk + the DB.
  • TTS chain. POST /api/tts + ttsOneSegment() tries Gemini TTS → Edge TTS → Google Translate TTS in order. Per-language voice maps. Language hint auto-detected from text if missing.
  • Auth. /api/auth/signup, /api/auth/login, /api/auth/me. JWT signed with JWT_SECRET, 30-day expiry.
  • Library API. Subjects, chapters, saved reels — all CRUD routes that proxy to db.js.
  • Health + version. GET /api/version returns the build SHA + feature flags so the client + curl can verify a deploy went out.
db.js
~440 lines·Postgres data layer
Postgres Neon Schema init

Every server.js route that needs to read or write the database calls a function defined here. Keeps SQL out of the route handlers.

What lives in this file
  • Schema bootstrapping. initSchema() creates the users, subjects, chapters, saved_reels, and chapter_assets tables if they don't exist — runs once on server boot.
  • Users. createUser, getUserByEmail, updateUserProfile, claimOrphanSubjectsFor (one-time claim for the first user on a fresh DB).
  • Library. listSubjects, createSubject, getSubject, updateSubject, deleteSubject, listChapters, getChapter, createChapter, deleteChapter.
  • Asset bytes. setChapterAsset, getChapterAsset, getSavedReelAsset — the image/audio bytes are stored in BYTEA columns so Render's ephemeral disk wiping doesn't lose anything.
  • Saved reels. listSavedReels, findSavedReel, createSavedReel, deleteSavedReel.

Frontend · Browser

The single-page web app the Capacitor WebView (and any browser) loads from Render. Three files do all the work — no framework, no build step.

public/index.html
~520 lines·Static markup, all screens
Single page All screens in one file i18n placeholders

The app's skeleton. Every screen the user can see — login, library, upload, loading, reels, error, plus all modals — lives inside one HTML file as separate <section> blocks that get toggled active by JS.

What's defined in this file
  • The screens. #login-screen, #library-screen, #upload-screen, #loading-screen, #error-screen, #reels-screen.
  • The modals. Paste-text, Ask-AI, Saved gallery, Library (legacy), App settings.
  • The bottom tab bar. Library · Generate · Settings — visible only on upload + library screens.
  • The customize panel. Two chip rows visible by default (Language + Style toggle); the disclosure reveals the rest.
  • i18n placeholders. Every translatable element carries a data-i18n or data-i18n-placeholder attribute — JS reads them and swaps the text from the EN / AR dictionary.
public/app.js
~3,800 lines·All client logic
Auth Reel rendering Audio / Karaoke Drag i18n Streaming SSE

The brain of the client. Big file, but logically organised top-to-bottom. Everything that responds to a tap, a scroll, or a network event lives in here.

Roughly in this order
  • Settings + i18n. DEFAULT_SETTINGS, the I18N dictionary (EN + AR), applyI18n(), theme toggles.
  • Auth. Sign-up / sign-in form, token persistence in localStorage, bootstrap on first load.
  • Upload flow. File drop, paste-text modal, generate button. Streams the SSE response from /api/upload-stream and calls appendStreamingReel() as each reel arrives.
  • Reel rendering. buildReel() creates the DOM for one reel — background image div, title, optional card, caption stage, etc. renderChunkedCaption() splits the narration into karaoke chunks.
  • Image + audio prefetch. ensureImage(idx) + ensureAudio(idx) POST to /api/image + /api/tts, cache the URL, and reuse it. Pre-warmed for the next few reels in the background.
  • Karaoke timing. speakReel() spins up a fresh new Audio(url), builds the word/chunk timing with buildTiming() using punctuation-aware wordWeight(), then drives the active-word highlight on every requestAnimationFrame.
  • Device-voice fallback. If every TTS provider fails, browserSpeakReel() uses the OS's SpeechSynthesis — language-aware so Arabic narration picks an Arabic system voice.
  • Drag handling. Note overlay + caption stage are draggable; uses raw touch events (not Pointer Events) so Chromium WebView's gesture compositor can't steal them.
  • Library + saved reels. Subject/chapter CRUD UI, calls server's /api/subjects + /api/chapters.
  • Quiz. Renders the end-of-deck quiz, scores it, persists stats to localStorage.
public/styles.css
~3,700 lines·5 themes, full styling
5 UI themes Light + Dark RTL support Phone-native layout

One stylesheet, organised by feature region. The bottom half is theme overrides — each UI theme (default, editorial, glass, riso, pastel) re-skins the same DOM.

What's defined
  • Layout primitives. Screens, upload card, drop zone, primary button, ghost button, chips, modals.
  • Reel UI. Reel container, background image layer, title wrapper, caption stage with karaoke chunks (.caption-chunk + .word), reel actions sidebar, reel meta bar.
  • Quiz UI. Quiz card, question, options, score card.
  • Library UI. Subject card, chapter row, profile card, library tabs.
  • 5 UI themes. body[data-ui-theme="default"], "editorial", "glass", "riso", "pastel". Each gets its own colour palette, fonts, shadows, accent treatment.
  • Light + dark variants. Each theme has both, switched by body[data-app-theme="light"] / "dark".
  • RTL. Selectors under html[dir="rtl"] flip alignments, swap left/right inset positions, fix flex directions for Arabic UI.
  • Aurora background. Soft radial-gradient blobs behind the upload screen for ambient color.

Config · Deploy

Small files, but they decide where the app runs and how it gets built.

package.json
npm dependencies + scripts

Lists every Node dep the server needs: express, @google/genai, msedge-tts, jsonwebtoken, bcryptjs, multer, pg, jszip, officeparser, @capacitor/core + @capacitor/android. The start script (node server.js) is what Render runs on boot.

render.yaml
Render Blueprint

Tells Render what to build (Docker via the Dockerfile), what environment variables are required (GEMINI_API_KEY, DATABASE_URL, JWT_SECRET), and to autoDeploy: true on every push to main.

Dockerfile
Render's container image

Two-stage build: a Node 22 base, npm ci for production deps, copy the source, expose port 3000, run node server.js. Render rebuilds the container on every push.

capacitor.config.json
Android shell config

Sets the appId (com.reelify.app), appName (Edu Shorts), the web directory the WebView serves, and — most importantly — the server.url that points at the live Render backend so the APK loads JS/CSS from there on every open.

CI · APK build

How a sideloadable APK gets minted from the repo on every push.

.github/workflows/build-apk.yml
GitHub Actions workflow

Triggers on every main push and on manual dispatch. Steps: check out the repo → install Node 22 + Java 21 + Android SDK → npm ci → optionally override capacitor.config.json's server URL → npx cap sync android to mirror the web assets into the Android project → ./gradlew assembleDebug → upload the resulting app-debug.apk as a workflow artifact.

Android · Native shell

The Capacitor-generated Android project that wraps the WebView. Most of it is auto-managed; only a few files matter day-to-day.

android/app/src/main/res/values/strings.xml

Holds the app's user-facing name (Edu Shorts) and the package identifier used at the OS level.

android/app/src/main/res/mipmap-anydpi-v26/ic_launcher.xml

The adaptive-icon spec for Android 8.0+. Points at the background and foreground drawables that get composed and masked by the launcher.

android/app/src/main/res/mipmap-*hdpi/ic_launcher_foreground.png

The actual rendered launcher icon image at five density buckets (mdpi, hdpi, xhdpi, xxhdpi, xxxhdpi) — produced by sharp from the source 1254×1254 PNG.

Extras

Helper pages and docs that aren't part of the app itself.

HANDOFF.md

Markdown document written for an incoming AI assistant. Describes the entire system — stack, repo layout, env vars, TTS chain, known issues — so a fresh session can pick up immediately without re-reading the codebase.

BUILD.md

End-user deploy instructions for fresh-installing the project from scratch (Render + Neon + GitHub Actions APK builds).

public/logo-picker.html

The 15-option launcher-icon preview page used to compare designs side-by-side at 96 px and 48 px before committing to one. Standalone — opens directly in any browser, no JS dependencies.

public/how-it-works.html

The companion to this page — explains the stack, the TTS chain, the delivery workflow, and the change-by-change journey. Lives next to the app so it's accessible via the live Render URL.

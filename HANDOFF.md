## What it is

**Edu Shorts** (originally branded "Reelify" — code still uses that name
for identifiers, see § Branding) is an AI-powered web app that converts
any educational document (PDF, DOCX, PPTX, image, plain text) into a
vertical scrolling feed of short "reels" — Instagram/TikTok-style. Each
reel pairs an AI-generated narration with karaoke captions, an
AI-generated phone-ratio background image, an interleaved quiz, and a
personal library to save them.

It's deployed on **Render** at <https://reelify-zgec.onrender.com>, with
**Postgres on Neon** for persistence and an **Android APK** built from
the same web codebase via Capacitor. The user installs that APK on a
Galaxy S24.

## TTS chain (the long-running pain point)

After many iterations, this is the current state in `server.js`:

```js
async function ttsOneSegment(text, voice, _voiceCustom) {
  const errors = [];
  try { return await ttsEdge(text, voice); }
  catch (e) { errors.push("edge: " + (e?.message || e)); }
  try { return await ttsGoogleTranslate(text, voice); }
  catch (e) { errors.push("gtts: " + (e?.message || e)); }
  throw new Error("All TTS providers failed — " + errors.join(" | "));
}
```

**Why it ended up here:**
1. **Gemini Flash Preview TTS** — has a hard ~10 RPM rate limit that
   isn't liftable by paid tier (because it's a preview model). Killed
   from solo chain. Still used for podcast (2-voice) mode where we
   splice raw PCM between turns.
2. **StreamElements** — was free no-key. Started requiring an API key
   in May 2026 (HTTP 401 "No API key was found"). Dead.
3. **ElevenLabs** — works but limited free tier (10k chars/mo).
   Pulled to keep things simple. Helper functions still in
   `server.js` for future re-enable.
4. **Google Cloud TTS / OpenAI tts-1** — paid upgrades. Same:
   helpers still defined, not in the chain.
5. **Microsoft Edge TTS** via `msedge-tts` package — free, neural
   voices. Works locally but on Render's shared IP range Microsoft
   silently drops the SSML response (returns 0 audio chunks → throws
   "Edge TTS produced no audio"). Still tried first because quality
   is much better when it works.
6. **Google Translate TTS** — `translate.google.com/translate_tts?
   ...&client=tw-ob` — unofficial endpoint, returns MP3, no auth.
   Quality is OK (single fixed voice, ~standard Google Translate
   voice). **Most recent addition, just deployed in `6223176` — the
   user hasn't confirmed yet that it actually works end-to-end.**

The `/api/tts` handler now surfaces the underlying error to the client
as `{ error, reason, code }` so the dbg overlay shows exactly which
provider failed.

### Client-side TTS rate limiter

`public/app.js` has `ttsThrottleAcquire()` — sliding window of 8 RPM
with a 60-second cooldown when a 503 quota error hits. This was added
back when Gemini was in the chain; it's harmless to leave on for the
new chain but the cooldown will basically never trigger now.

### Caption sync

Edge MP3s ship with ~80–120 ms of leading silence. `speakReel()` in
`public/app.js` applies a **180 ms lead** to `audio.currentTime` so the
active chunk lights up just before the audio is heard. Also rebuilds
the chunkData on `durationchange` because MP3 duration starts as a
bitrate estimate and firms up after a chunk loads.

## Reel pipeline (server side)

1. `POST /api/upload-stream` — accepts a file, extracts text (JSZip
   primary path for OOXML, officeparser fallback, native Gemini for
   PDFs/images), sends the AI a structured prompt (in `buildReelPrompt`)
   and streams the response back as SSE.
2. Streaming parser (`findReelsArrayStart` + `extractCompleteReels`)
   walks the partial JSON and emits each fully-formed reel object as
   it appears, so the user can start watching while the rest streams.
3. At end-of-stream, `extractQuizArray` pulls the `"quiz": [...]`
   array out of the full buffer even when the surrounding JSON failed
   to parse (this was the "quiz never appeared" bug fixed in `ba69b21`).
4. If a subject was selected, the full chapter (reels + quiz +
   settings + filename) is persisted to the `chapters` table.

Image and audio assets generated subsequently via `/api/image` and
`/api/tts` are written to **Render's ephemeral disk** at
`generated-images/` and `generated-audio/`. They are also persisted to
Postgres in `saved_reels.image_data` / `saved_reels.audio_data` (when
the user saves a reel) and in the `chapter_assets` table (every
generation that happens inside a chapter context). After a redeploy
wipes the ephemeral disk, **saved reels and chapter reels reload bytes
from Postgres** via `/api/saved/:id/{image,audio}` and
`/api/chapters/:id/asset/:kind/:idx` — no regen needed.

## Client-side reel flow

1. `appendStreamingReel(reel)` builds the DOM + kicks off ensureImage
   and ensureAudio in the background.
2. `IntersectionObserver` on each reel fires `activateReel` when the
   user scrolls one to ≥ 70 % visibility.
3. `activateReel` calls `paintReelImage` (sets `background-image`
   directly the moment the URL is ready — no probe step), and
   `speakReel` from inside `ensureAudio.finally(...)` so audio.play()
   fires close in time to the network completion (keeps Chromium
   WebView's autoplay-grace window valid — that was the "voice doesn't
   play" bug fixed in `81358eb`).
4. `speakReel` uses a fresh `new Audio(url)` per reel. AbortController
   removes its event listeners cleanly in `stopAudio()` so the
   previous reel's `ended` / `pause` / `play` callbacks can't mutate
   state on the now-active reel.
5. Karaoke timing built once on `loadedmetadata` then rebuilt on
   `durationchange`. tick() uses `audio.currentTime + 0.18s` to apply
   the Edge-lead-silence offset.
6. If `ensureAudio` returns null (all providers failed), `speakReel`
   falls back to `browserSpeakReel` which uses `speechSynthesis` with
   a pre-warmed voices list, explicit `lang`, explicit voice pick from
   `getVoices()`, and `speechSynthesis.cancel()` before each speak to
   flush phantom queued utterances.

## Audio dbg overlay (debugging tool)

A small green dot in the bottom-right corner of the screen toggles a
black strip near the bottom of the reel UI that logs every audio
event in real time:

```
unlockAudio fired
unlock silent play OK
ensureAudio idx=0 POST /api/tts
ensureAudio idx=0 OK url=/audio/tts_xxx.mp3
startSpeak idx=0 via=ensureAudio.finally
speakReel 0 start, cached=true
speakReel 0 got URL, starting Audio
audio.play() OK reel 0 muted=false vol=1
```

…or on failure:

```
ensureAudio idx=0 FAIL 500 HTTP 500 Voice generation failed ::
  All TTS providers failed — edge: Edge TTS produced no audio |
  gtts: HTTP 429
```

The whole strip is gated by `localStorage.getItem("edu-audio-dbg")` so
the user can leave it on and screenshot when things break. The
implementation is `audioDbg()` in `public/app.js` near `showToast`.

## Drag handling (long-press to move note / captions)

`makeDraggable()` in `public/app.js`:
- Bound on `.reel-card` (note overlay) and `.reel-caption-stage`.
- Uses **raw touchstart / touchmove / touchend** on Android, NOT
  PointerEvents. The compositor in Chromium WebView cancels pointer
  events the moment it decides a touch is a vertical pan, even with
  setPointerCapture. Touch events still fire and `preventDefault()` on
  touchmove (with `{ passive: false }`) wins.
- Long-press is 150 ms (was 220).
- `.reel-card` has `touch-action: none` in CSS so the browser never
  tries to scroll on touches that land on the card. Caption-stage
  stays `touch-action: pan-y` because it's much larger.
- Mouse path kept separate for desktop.

## How to deploy

The user already did the one-time setup. Just `git push origin main`
and Render auto-deploys (`autoDeploy: true` in `render.yaml`). First
deploy of a session takes ~3 min if npm install runs new deps;
otherwise ~90 sec. Render's free tier sleeps after 15 min idle and
takes 30–60 s to wake up on the first request.

The APK build is on-demand: GitHub repo → Actions tab → "Build
Android APK" → Run workflow → paste the backend URL → wait ~5 min →
download from the workflow artifacts. The APK is just a Capacitor
shell pointed at the Render URL — **rebuilding the APK is almost
never needed because the WebView loads fresh JS / CSS on every open**.
